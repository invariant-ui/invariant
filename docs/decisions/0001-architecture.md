# ADR 0001: Foundational architecture

Status: Proposed (awaiting approval)
Date: 2026-10-30
Related: `docs/architecture/system-architecture.md`, `docs/architecture/primitiv-analysis.md`

## Context

Invariant compiles React, Angular, and Vue libraries, Storybook, Figma, and zeroheight into a framework-independent design-system contract. The closest prior art, Primitiv, is React-only, has no intermediate representation, attaches provenance per entity rather than per fact, and ships compiler and MCP server in one package. We need to decide the shape before writing code.

Note on inputs: the implementation plan was not in the repository when this ADR was first drafted and was supplied afterward. Decisions below marked "revised" were changed to match it. The root `CLAUDE.md` (also supplied afterward) is consistent with this ADR; in particular its rules that LLMs are never authoritative for extractable facts and that inferred rules are never auto-promoted to approved policies are adopted as written.

## Decisions

### D1. Pipeline: adapters emit an IR; a pure compiler builds the contract

Adapters produce IR documents (entities, facts, evidence, diagnostics). `core` is a pure function from IR, config, and approvals to contract. Adapters never merge or resolve and do not know about each other.

Consequences: adapters and compiler are tested independently with golden files; network sources can be replayed from snapshots. Cost: an additional schema to design and version, and a mapping step in every adapter. We accept this because it is the only way to add a source without touching the others.

### D2. Every fact carries a status: `discovered | documented | inferred | approved`

- `discovered`: machine-parsed from an artifact whose structure is the claim.
- `documented`: human-authored prose or guidance in a doc surface.
- `inferred`: derived by a named deterministic rule; never emitted by an adapter.
- `approved`: explicitly accepted by a human, stored in a committed approvals file and bound to a fingerprint of the fact.

Consequences: consumers (including MCP clients) can weight facts by trust. Approvals invalidate automatically when evidence changes. Cost: the `discovered` vs `documented` boundary needs judgment for some inputs, for example a Figma variable's value is `discovered` (API structure) while its description is `documented`. The adapter sets `origin`; the rule is in the system architecture doc.

Open: whether `approved` replaces the underlying status or layers over it. Proposed: it layers, so the contract keeps both the approval and the status the fact had when approved.

### D3 (revised). Evidence is separate and referenced by id; timestamps are allowed but excluded from the content hash

The plan requires timestamps in contract metadata, in source synchronization data, and on evidence, and lists `invariant.evidence.json` as its own artifact. Therefore:

- Contract facts carry `evidenceIds`. Evidence entries live in `invariant.evidence.json`, keyed by an id derived from `(source, locator, extractor, contentHash)`. An entry also carries method, original evidence excerpt, optional `confidence`, `verificationStatus`, and `capturedAt`.
- The contract has `metadata.compiledAt` and `sources[].lastSyncedAt`. The contract's `contentHash` is computed over canonical JSON with those timestamp fields removed. `verify` and incremental compilation compare `contentHash`, not bytes.
- Absolute paths and hostnames never enter the contract or evidence; paths are POSIX-relative to a recorded source root.

Consequences: determinism is defined over the hash, which still gives replayable builds and meaningful diffs. Cost: two files must travel together for full provenance, so the contract must remain valid and useful alone (facts keep status; evidence resolves by id and a missing evidence file yields a diagnostic, not an invalid contract). This also honors plan principle 7 (portable output).

### D4. Conflicts are records; resolutions are overlays

Unequal values at one `(subject, path)` always produce a conflict listing every asserted value and its evidence. Resolution (`pending`, `by-precedence`, `approved`) is stored beside the conflict. The losing value is never deleted. Absence is a conflict only when the other side's source status is `ok` and its field completeness is `complete`; otherwise it is a diagnostic.

Consequences: no silent overwrite, and a failed or partial source cannot imply a fact was removed. Cost: larger contracts and more records for consumers to filter. Primitiv's `Conflict` type mixes identity and field resolution and carries compatibility fields; we avoid that by separating the two from the start.

### D5. Network-bound sources must have a snapshot path (Figma, zeroheight, served Storybook)

Verified: Figma Variables endpoints are limited to full members of Enterprise orgs; zeroheight's API is unavailable on Free and Starter plans. Therefore each such adapter supports compile from a saved raw response, and live fetch writes that snapshot.

Open: whether Figma should also accept a plugin or tokens-export file as an input for non-Enterprise users. Not verified; decide when the Figma adapter milestone starts.

### D6. Extraction engine: TypeScript compiler API for React and Angular; `vue-component-meta` for Vue

Primitiv's Babel-based resolver is explicitly a "deliberately small" subset of TypeScript shapes. The checker gives real type resolution at the cost of speed and a resolvable `tsconfig`. `vue-component-meta` (verified: props, events, slots, exposed, via a tsconfig or inline JSON config, TypeScript peer dependency) already does the Vue case.

Consequences: higher fidelity; a shared TypeScript major-version coupling across adapters, to be managed with a peer-dependency range. Cost: extraction requires the target project's types to resolve. A degraded syntactic mode is deferred, not promised.

### D7. Static extraction only; never execute target code

Adapters parse, they do not import or run component modules, Storybook configs, or story files. Storybook args and controls come from static CSF parsing and from the built `index.json`, not by executing stories. Values that cannot be resolved statically are marked `completeness: unknown` rather than guessed.

Consequences: safe on untrusted repositories, deterministic. Cost: dynamically built args are not captured.

Revised for config: the plan's example config is `invariant.config.ts` using `process.env`. The rule above governs analysis of target repositories, not the user's own config. Decision: JSON config is the default and is parsed, not executed, with `${env:NAME}` interpolation for secrets. `invariant.config.ts` is also supported but is an explicit, documented code-execution surface: it is loaded only from the project being configured, never from a scanned source, and `invariant compile --config-json-only` refuses it (for CI on untrusted checkouts). Primitiv's equivalent is an opt-in data-only mode; ours inverts the default.

### D11. Semantic analysis is a recorded, replayable stage outside the deterministic core

The plan allows LLMs to classify documentation, resolve entities, and explain conflicts, and the root `CLAUDE.md` forbids them from being authoritative for extractable facts. Therefore `semantic-engine` emits **proposals** (entity links, classifications, inferred relationships) with evidence ids, `confidence`, a reasoning summary, `status: inferred`, and `requiresApproval`. Each proposal records model id, prompt hash, and input hashes, and is stored as a content-addressed artifact. The deterministic compiler consumes stored proposals as input and never calls a model. Re-running compile without re-running semantic analysis is byte-for-byte reproducible. Proposals never override `discovered` facts; a disagreement becomes a conflict. Inferred organizational rules are never promoted to `approved` except by an explicit human approval record.

Consequences: LLM nondeterminism is quarantined and auditable; reviewers can diff proposals. Cost: a proposals store and a staleness rule (a proposal is invalid when its input hashes change).

### D12. Contract versioning, immutability, and incremental compilation

Contract schema versions are semver with migrations (`CLAUDE.md`: all contract changes are versioned). A published contract is identified by its `contentHash` and records source versions (git commit, package version, Storybook version, Figma file version, zeroheight page versions where the API exposes them). Published contracts are never edited; a recompile produces a new contract. Incremental compilation skips per-source extraction when a source's input hash is unchanged and re-runs only cross-source stages.

Consequences: traceability required by plan principle 10. Cost: source version capture is uneven; where a source exposes no version, the contract records that explicitly rather than inventing one.

### D8. MCP is a consumer: `@invariant/mcp` depends only on `@invariant/contract`

It cannot import `core` or any adapter, enforced by a dependency-boundary check in CI. All tools are read-only; responses carry the contract hash and per-fact status.

### D9. Monorepo layout and tooling

pnpm workspaces, strict TypeScript, ESM only, Vitest, Biome, project references. Package structure and dependency direction as in the system architecture doc. Package names follow the plan (`compiler-ir`, `compiler-core`, `compiler-<source>`, `apps/cli`, `apps/mcp-server`, and so on). Start minimal: `contract`, `diagnostics`, `compiler-ir`, `compiler-core`, `apps/cli`; add each other package when its milestone starts. `apps/api` is deferred. Config loading lives in `apps/cli` until a second consumer exists.

### D10. Component identity across sources is explicit-first

Order: explicit mapping file, then adapter-provided stable cross-reference, then unambiguous exact normalized-name match. Otherwise emit a `could-not-link` diagnostic and do not merge. This adopts Primitiv's conservative approach.

## M0/M1 implementation addendum (2026-10-31)

Decisions made while implementing the first two milestones. None changes a decision above; they refine it.

- **Layered approval is encoded as `status: "approved"` plus `approval.priorStatus`** (resolves U2). The four-valued status the plan requires is preserved, and the underlying status is retained for audit. An approval carries a fingerprint of (entity id, path, value); `verifyContract` reports `contract.approval-stale` when it no longer matches.
- **Per-field facts are a sidecar map** on each entity (`facts[path]`), not wrapped values (resolves U5). Entities stay plainly typed and readable; trust metadata attaches by fact path. Cost: fact paths must resolve, which is validated.
- **`shared` exists and `contract` may depend on `shared` and `diagnostics`.** Hashing and canonical JSON are part of the contract's definition (the content hash), so they need a home both `contract` and `compiler-ir` can use. The boundary rule is updated accordingly and enforced by `scripts/check-boundaries.ts`.
- **Plan "source versions" metadata lives on `sources[].version`**, not duplicated in `metadata`, to avoid two places that can disagree.
- **`compiler-core` and `apps/cli` were not created at M0.** No code needed them yet. They start at M2 and M3.
- **JSON Schema drift is checked by golden-file tests** (regenerate with `pnpm update:golden`) instead of a separate generation script. Fixtures are validated against the generated JSON Schema with Ajv (dev dependency, tests only).
- **Toolchain versions** pinned at M0: Node 24 (`.nvmrc`), pnpm 12.16.1, TypeScript 7.0.2, Zod 4.6.7, Vitest 5.0.5, Biome 2.6.4. TypeScript 7 handled `tsc -b` project references and `NodeNext` without issue.
- **Biome ignores markdown** so formatting never rewrites documentation.

## Phase 2 implementation addendum (2026-10-31)

- **TypeScript is pinned to 5.9.3 repository-wide, superseding the M0 pin to 7.0.2.** D6 requires the TypeScript compiler API. The `typescript` 7 package ships no stable JavaScript API: its `.` export is only a version shim, and the programmatic entry points are `typescript/unstable/*`, which drive a native binary. Phase 2 needs `createSourceFile`; Phase 3 needs the type checker. 5.9.3 is the latest 5.x release, has the stable API, and also keeps `ts-morph` an option. D6 is unchanged in intent. Revisit when the TypeScript 7 API stabilizes; the cost of waiting is that analysis cannot understand syntax newer than 5.9.
- **IR is now 1.1.0.** Entity kinds `package`, `export`, `config`, and `token-file` were added so discovery results are represented without mislabelling an export as a component. Readers accept only the exact version, so older IR documents are rejected until regenerated; there are no consumers of 1.0.0 yet. Added `computeIrContentHash`, which excludes evidence capture times.
- **Discovery runs once and is shared.** Adapters receive `ProjectDiscovery` in their context. This keeps adapters independent of each other while avoiding repeated filesystem walks. The built-in inventory adapters read nothing beyond the discovery result.
- **Inventory adapters, not framework adapters, close Phase 2.** The exit criterion (project discovered and represented in IR without a framework adapter) is met by four neutral adapters (npm packages, Storybook config, token files, Markdown). They never assert that an export is a component; that is Phase 3 work.
- **`artifact-generator` was created now** (the architecture doc deferred it until a second artifact existed): the compiler now emits project, IR, diagnostics, and manifest artifacts. It depends only on `shared`; `compiler-core` does not know it exists, and the end-to-end test lives in `scripts/` for that reason.
- **Timestamps live in the manifest and in evidence `capturedAt` only.** `compile` takes an injectable clock; `irContentHash` makes unchanged inputs comparable across runs.
- **Existence checks are case-exact** (walked file list) because a real fixture exposed that `exists("Button.ts")` was true on macOS when only `button.ts` existed.
- **Scope boundaries**: reconciliation and contract generation (my earlier M2) are not done; incremental compilation is not implemented, only the hashes that enable it; "isolating build and rendering" has no subject until an adapter builds or renders anything.

## Phase 3 implementation addendum (2026-10-31)

- **Raw TypeScript compiler API, not `ts-morph`.** The wrapper offered nothing the direct API did not, and it is one fewer dependency. The program contains only the package's own files; `node_modules` (including `@types/react`) is not loaded. Consequence: props inherited from third-party types are reported as inherited (`inheritedPropsFrom`, `propsComplete: false`) rather than enumerated. On Radix Primitives this affects 190 of 227 components. A type-aware mode that reads installed `.d.ts` files read-only would fix most of it; it is deferred because it widens what analysis reads, and it needs its own decision.
- **JSDoc prose is `authored`; structure is `extracted`.** Descriptions, `@deprecated`, and `@example` become `documented` facts; names, types, defaults, and domains become `discovered`. This keeps "documented" meaning "a person wrote it", even when it lives in source.
- **`compiler-tokens` is a new package** (the plan's layout has no token package; its Phase 3 lists token extraction under the React compiler). Tokens are not React-specific, so folding them into `compiler-react` would have forced Vue and Angular to depend on it. The React adapter extracts styling references; `compiler-tokens` extracts token definitions.
- **Event-handler props stay props.** Neutral `events` mapping (React `onPress`, Vue emit, Angular output) is deferred to reconciliation, where all three exist.
- **Completeness is explicit.** `propsComplete` and fact-level `completeness` mean "absent does not imply nonexistent". Usage facts never claim `declared: false` against an incomplete props set.
- **Unknown is reported, not dropped.** Higher-order components, factory-made components, wildcard subpaths, and unaddressable prop names each produce a diagnostic.
- **Compound children are components** named `Root.Child`, linked to their root.
- **Open decision U17: contract domains for styling, usage, and render relationships.** Contract v1 has no field for `styling.*`, `usage.*`, or `composition.renders`; the IR carries them under neutral paths. Options: (a) an additive contract 1.1 adding style/token references and observed usage (recommended: it benefits Vue and Angular too), or (b) store them under `extensions`, which keeps the contract unchanged but hides framework-neutral data. Must be decided before contract generation.
- **Real-library validation found defects the fixture did not**: `React.FC` components returning `cloneElement` and annotated components with non-JSX returns were missed. Both are fixed with tests. Re-running a real library after each adapter change is part of the workflow.

## Phase 4 implementation addendum (2026-10-31)

- **Story identity is the export, and nothing is synthesized.** Storybook's documentation says the named export determines the id, but does not document the id or derived-name algorithms (and its own examples disagree on digit splitting), so the adapter never produces story ids or derived display names. `story.name` exists only when explicit. A built `index.json` (not documented as public API) is read tolerantly as optional evidence and is not used for identity.
- **IR 1.2.0** adds the entity kind `story-group` for a CSF `meta`. Hard-coded IR version literals in `compiler-core` were replaced by the exported constant so a future bump touches one place.
- **TypeScript analysis moved to `compiler-core`.** The type-checking program (`createAnalysis`, with workspace-package path mapping) and the generic AST helpers are shared by the React and Storybook adapters, so adapters stay independent of each other (the dependency rule forbids `compiler-storybook` importing `compiler-react`).
- **Neutral component link key.** Component sources publish `implementations.<fw>.extensions.<fw>.{file,localName}`; story sources publish `group.component.{file,name}`. Linking matches on that pair, never on display names. This is the convention Vue and Angular must follow.
- **`reconciliation` created now, narrowly.** Plan Phase 4 requires Storybook/code discrepancy diagnostics, which need cross-source comparison; adapters cannot see each other, so the comparison lives in a package that consumes IR only. It currently contains only the Storybook checks and linking. The rest of plan Phase 7 (entity resolution across all sources, conflict records, governance, semantic classification) is not started.
- **Claims are conservative and evidence-backed.** Undeclared-name claims require `propsComplete: true`; arg-level claims require the default render (a custom render's args may belong to another component); mapped args and unresolved values are never checked; each finding carries evidence from both sides. The default-render rule was a defect found by running on a real design system, not by the fixture.
- **Real-library validation again found defects fixtures did not** (a crash on CSF 2 assignment annotations, and the custom-render false positive). Running a third-party library after adapter changes remains part of the workflow.
- **Open decisions carried forward:** U17 (contract fields for styling, usage and render relationships) and the type-aware mode for reading installed `.d.ts` files remain undecided and now also limit how many Storybook claims can be verified.

## Phase 6 implementation addendum (2026-10-31)

- **Vue: the official SFC parser plus the TypeScript API, superseding the earlier note in D6 to wrap `vue-component-meta`.** `vue-component-meta` requires a real `tsconfig` and installed `vue` types, which contradicts the project-files-only, read-only analysis used by every other adapter. Each SFC's script is analyzed as a virtual TypeScript module; macros are read from the syntax tree and types resolved through the checker. `@vue/compiler-sfc` (MIT, no install scripts) is the one added runtime dependency, justified because hand-parsing SFC blocks is error-prone. `vue-component-meta` remains a possible cross-check.
- **Angular: static decorator metadata through the TypeScript API and a small template scanner, not `@angular/compiler`.** It is heavy and is not a stable tooling surface. `standalone` is recorded only when written, because Angular's documentation page for `@Component` does not state its default.
- **Shared analysis moved to `compiler-core`**: the static evaluator (`evaluate`), literal-domain and member description (`describeMember`, `ownProperties`, `externalBases`), and a neutral component-fact writer (`ComponentFacts`), so adapters stay independent and emit identical paths. `externalBases` now treats `import("pkg").Type` as external for every framework.
- **IR 1.3.0** adds the entity kind `module` (Angular NgModules).
- **Discovery reads `ng-package.json`** (`lib.entryFile`) and the conventional `public-api` file names when a package declares no entry, since ng-packagr source manifests usually declare none. Nothing else is guessed.
- **Events are neutral for Angular and Vue and ordinary props for React**, deliberately and with a test; unifying them belongs to reconciliation.
- **Component link key is shared by all three frameworks and Storybook.** Vue uses the PascalCase file name as `localName`; Storybook links a story's `.vue` import with the same pair via a shared helper (`componentNameFromFile`).
- **Defects found by fixtures this phase**: `PropType` casts were stripped before being read (so enum props became plain strings); Angular control-flow conditions such as `@if (a<b)` were read as tags and swallowed the next element; ng-packagr entries were not discovered; decorator inputs without a written type were left `unknown`. All fixed with tests.
- **tsconfig `paths` are honored by every source adapter** (`tsconfigPaths` in `compiler-core`: follows `extends` and `references`, resolves against `baseUrl` or the config directory, ignores package-name `extends`). Adapters now also load `tsconfig*.json` as inputs, which changed `inputHash` in the React and Storybook goldens (regenerated). Vue maps `.vue` imports to virtual script modules.
- **Real-library validation done**: reka-ui (Vue, 395 components, 19 incomplete generics) and ng-bootstrap (Angular, 52 components, 20 modules). Remaining limit: third-party types are not loaded, so `inject()`-based Angular defaults stay `unknown`. An opt-in type-aware mode that reads installed `.d.ts` files is an open decision. See `docs/specifications/angular-and-vue-v1.md`.

## Phase 7 implementation addendum (2026-10-31)

Phase 7 is the first phase that produces a contract. Decisions:

- **No contract schema change.** Contract 1.0.0 already holds everything Phase 7 needs. Neutral IR facts that the contract has no field for (`styling.*`, `usage.*`, `composition.renders` detail, the raw `extensions.*` of non-framework namespaces) are carried under `component.extensions.invariant` with facts that cite their evidence. Open decision U17 (promote these to first-class contract fields) stays open and is unchanged. Compatibility: none affected, no migration.
- **`reconciliation` builds the contract from IR.** Entity resolution, merge, conflict detection, sources, evidence file, review queue. Deterministic only. It does not call a model.
- **Identity rules are ordered and recorded.** (1) The framework link key `{file, localName}` identifies one implementation (unchanged). (2) Implementations in different frameworks merge into one conceptual component only on an equal normalized name (case and separators ignored, after removing a design-system prefix shared by most components of a source). Every such merge is an `inferred` fact on `implementations.<id>` with rule, reasoning and confidence. (3) Any name that matches more than one candidate in a framework is not merged; an `identity-ambiguity` conflict is recorded instead. Same-name components in one framework are never merged.
- **Conflict policy.** When sources disagree on a path, the contract keeps one value and a conflict record holds every claim. The kept value is chosen by fixed precedence (`discovered` over `documented`, then lowest source id) and the conflict stays `open`. Nothing is dropped. API absent from some implementations whose props are fully known is an `existence-mismatch` of severity `info` (frameworks legitimately differ); a different value is a `value-mismatch` of severity `warning`. Storybook discrepancies that cite evidence on both sides become conflicts; coverage findings stay diagnostics, because a conflict needs two evidenced claims.
- **`semantic-engine` is additive and deterministic first.** It classifies token categories, classifies documentation pages into guidelines, and infers compound-component containment. Every output is an `inferred` fact with rule, reasoning, inputs, confidence and existing evidence. A post-condition check proves enrichment only adds: no existing fact record or value changes, except the placeholder token `category`. Policies are never produced. Model-assisted classification is not implemented; when added it must pass the same checks and carry `derivation.model`.
- **Review metadata is a derived artifact, not contract content.** `buildReviewQueue(contract)` lists open conflicts, inferred identity links and inferred facts with confidence, evidence and an approval requirement. Rejecting an inference has no representation in the contract yet; that belongs to Phase 10 governance.
- **zeroheight and Figma are absent.** Phase 7 runs on code, Storybook, tokens and Markdown. Its rules take no source type as an assumption, so those sources add claims later through the same path. The plan's exit criterion names zeroheight, so it is met only for the sources that exist.
- **Documentation classification reads the page title and file name only.** Headings were tried and rejected after a real library (reka-ui) showed component pages with a "Keyboard Interactions" section being classified as accessibility guidelines.
- **Orchestration stays out of `compiler-core`.** `compile()` still stops at IR (boundary rule). Phase 8 owns the CLI that calls `compile`, `reconcile`, `enrich`. Until then `scripts/compile-dev.ts --contract` and the Phase 7 end-to-end test do it.

## Phase 8 implementation addendum (2026-10-31)

- **`apps/cli` owns orchestration.** It is the first package allowed to depend on every compiler, reconciliation and the semantic engine. `compile()` in `compiler-core` still stops at IR; the CLI runs compile, reconcile, enrich, verify. Boundary rules register `@invariant/cli` explicitly. No other package may depend on it.
- **No CLI framework.** Argument parsing uses `node:util` `parseArgs` in strict mode. No new runtime dependency was added.
- **JSON configuration by default; code configuration needs `--trust-config`.** The plan shows `invariant.config.ts` reading environment variables. Loading it executes code, which would break the rule against running customer code if the CLI were pointed at a repository it does not own. JSON is data and always loads; a TypeScript or JavaScript config loads only when the user passes the flag. Compatibility: the plan's TypeScript example works with the flag, and no schema changes.
- **One project, scoped sources.** Configuration entries limit adapters by path rather than compiling separate projects, because story-to-component links use project-relative file paths and need one shared root. Entry ids are labels; compiled source ids stay adapter-generated, and the CLI prints the mapping.
- **`zeroheight` and `figma` are rejected in configuration** with an explicit message instead of being accepted and ignored.
- **`ArtifactEntry` may carry `text`.** `artifact-generator` gained a verbatim text variant so the HTML report is listed in the manifest with its hash. Additive; JSON entries are unchanged.
- **Report is a static, escaped view.** No scripts or external requests. It is never an input to anything.
- **Review queue is a file, not a command.** `invariant.review.json` is written; approval workflows are Phase 10.

## Phase 9 implementation addendum (2026-10-31)

- **MCP is a consumer.** The server reads the compiled contract and evidence files from the output directory. Nothing in `contract`, `compiler-ir`, `reconciliation` or the adapters knows MCP exists. Queries and validators live in a protocol-free package (`contract-query`) so any other consumer can reuse them.
- **Package layout differs from the plan.** The plan lists `apps/mcp-server`. Instead: `packages/contract-query` (read model, search, validators), `packages/mcp` (protocol, tools, resources, stdio runner), `packages/agent-kit` (skills and integration files), and the CLI hosts the server as `invariant mcp`. A separate app would only repeat what the CLI already provides, and one extra executable adds nothing to ship. Boundary rules register the new packages; `contract-query` and `agent-kit` cannot import `mcp`.
- **No MCP SDK dependency; the stdio subset is implemented directly.** The current specification revision (2026-07-28) is stateless: no `initialize`, a required `server/discover`, protocol version in each request's `_meta`, `resultType` in results, and error `-32022` for an unsupported version. Revisions up to 2025-11-25 use the `initialize` handshake. The server is dual-era: a request carrying the modern `_meta` is served by the modern rules; an `initialize` request selects legacy rules for that process. The subset needed here (initialize, ping, server/discover, tools/list, tools/call, resources/list, resources/read, resources/templates/list) is small, and tests pin the wire format against the specification text. Cost: protocol drift is ours to track. Re-evaluate if the server needs sampling, elicitation, subscriptions or HTTP, which are out of scope.
- **Transport is stdio only.** No network listener, no authentication surface. HTTP is deferred.
- **Everything is read-only and deterministic.** All tools carry `readOnlyHint`. There is no search model or embedding: search is lexical and ranked by fixed rules. Tool results always include the contract hash and the status (discovered, documented, inferred) of what they report. An incomplete API (`propsComplete: false`) is reported as unverifiable, never as absence.
- **Tool output is untrusted data.** Names, descriptions and guideline titles come from customer source and documents and can contain instructions aimed at a model. The server states this in its `instructions`, marks results with `_meta["com.invariant/provenance"].untrustedContent`, and returns JSON rather than prose. Generated skills and rules contain only sanitized names and identifiers from the contract, never free text, so a hostile description cannot be written into committed agent configuration.
- **Validators are static.** `validate_design_system_compliance` parses a code snippet (TypeScript API for JSX, a small linear scanner for Vue, Angular and HTML templates); it never executes it. It checks only literal values and says what it could not verify. It applies no policy, because no approved policies exist until Phase 10.
- **Integration files are generated, never maintained.** Claude Code: `.mcp.json` and `.claude/skills/`. Cursor: `.cursor/mcp.json` and `.cursor/rules/*.mdc`. Codex: project `.codex/config.toml` (trusted projects only) and a marked section of `AGENTS.md`. Windsurf: a rules file only; its MCP configuration location could not be verified from current documentation, so a snippet is printed instead of written. Files are written only inside the project. Existing user files are merged (JSON) or left alone, never replaced without `--force`.

## Phase 10 implementation addendum (2026-10-31)

- **`invariant validate` now validates application code**, as the plan's exit criterion states. The Phase 8 command that checked the compiled output is renamed `invariant verify` (same checks, same `--fresh`). This is a deliberate breaking change to a command that is one phase old; `validate` with no paths fails with a pointer to `verify`. Nothing outside this repository depends on it.
- **No contract schema change.** Organizational rules are carried by existing entities: a machine-readable rule is a `constraint` (kind, subjects, `details`, and the normalized rule under `extensions.invariant.rule`), and a `policy` wraps constraints with the mandatory approval block, severity and enforcement. A policy without approval still cannot be represented. Policies come from a human-written, version-controlled `invariant.policies.json`; nothing infers a policy.
- **New packages.** `validation` (scanners, rules, policy evaluation, reporters) takes over the validators that Phase 9 placed in `contract-query`, which stays a read model; `mcp` and the CLI use `validation`. `governance` (policy compilation and decision application). Boundary rules: `validation` may use `contract`, `contract-query`, `shared`; `governance` only `contract`, `shared`, `diagnostics`.
- **Rule set.** The eleven plan rules map to codes (see `docs/specifications/validation-and-governance-v1.md`). Rules that need data the compilers do not produce are wired and tested but dormant until that data exists: `requires-parent` relationships, accessibility requirements, and layout patterns have no producer, so they are enforced only through approved policies.
- **Unknown component is decided by imports, not names.** A JSX tag is an unknown design-system component only when it is imported from a package the contract publishes. A tag with no such import is never called unknown.
- **Decisions are data in git, applied at compile.** Approvals, rejections and conflict resolutions are written by `invariant review ...` to `invariant.decisions.json` and applied on every compile, so the contract stays reproducible from sources plus two human-authored files. A decision records the value it was made about; if that value changes, the decision is stale, is not applied, and is reported. Approving layers `approved` over the prior status with the contract's own fingerprint. Rejection is supported where removal is well-defined (inferred containment links, inferred guideline links, inferred token categories); rejecting an inferred cross-framework identity would require splitting a component and is refused with an explanation. A conflict resolution records a decision; it does not rewrite the kept value, because the fix belongs in the source and the conflict disappears on recompile.
- **Approver identity is asserted, not authenticated** (open decision U14). `--as <name>` or `INVARIANT_USER` is required; an optional `governance.approvers` allowlist in configuration rejects other names. Real enforcement is the repository's review process over the two files (for example CODEOWNERS). The documentation says so.
- **Severity is configurable per rule** (`validation.rules`, including `off`), and policy enforcement can lower it (`warn` caps at warning, `report-only` is info). Defaults are conservative: heuristics are never errors.
- **CI support is exit codes and report formats**: `--format text|json|github|sarif`, `--fail-on error|warning|never`. No workflow file is generated, because the tool is not published and a generated install step would be invented.

## Plan order change (2026-10-31)

The owner moved plan Phase 5 (zeroheight compiler) to after plan Phase 10. Consequences: the plan's MVP definition (React, Storybook and zeroheight compiled into one contract) is not met until zeroheight lands; reconciliation (Phase 7) is built and tested with code and Storybook sources only, so its entity resolution and conflict model must not assume a documentation source exists; and the CLI, MCP server and validation (Phases 8 to 10) ship without zeroheight guidance, so `documented` facts come only from JSDoc, Storybook docs and Markdown until then. U9 remains the blocker for zeroheight.

## Alternatives considered

- **Fork Primitiv.** Rejected: React-only analysis core, no IR, per-entity provenance, and a CommonJS single-package layout would each need rewriting. Its ideas are adopted; its code is not copied.
- **No IR (adapters return contract fragments).** Rejected: this is Primitiv's design and makes adding a source an edit across the builder and shared types.
- **Single `confidence` score instead of statuses.** Rejected: a score hides why a fact is trusted. Statuses are categorical and auditable.
- **Cloud-hosted compile or store.** Rejected by requirement.

## Status of this ADR

Accepted for M0 and M1 on 2026-10-30 with the proposed defaults for U2 (approved layers over underlying status), U3, and U5 (per-field facts). Later milestones remain subject to the open items above.
